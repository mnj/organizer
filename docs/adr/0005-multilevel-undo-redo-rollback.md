# Multi-level undo (50) with redo, move-back + log rollback, Action Bar

Undo is a multi-level LIFO stack up to 50 entries (or queue length) with redo (`Ctrl+Shift+Z`/`Ctrl+Y`). Each entry stores `hash`, `src_name`, `dest_path`, `was_duplicate`, `folder_txt` (the `SourceFolder/<folder>.txt` that was appended). On undo we `rename` the file back from `../<folder>/` or `../duplicate/` to `SourceFolder/src_name`; if a name clash exists we suffix `_undo_1`, `_undo_2` (never overwrite). If it was not a duplicate, we remove the hash’s last occurrence from that `SourceFolder/<folder>.txt` (read, filter last matching line, `flock`+`fsync` rewrite) and remove it from the in-memory union `HashSet`; duplicate-routed undos skip log/HashSet. We push the entry to the redo stack, make the file Current File again (adjust queue index), and toast “Undid <Action>: foo.jpg → Source”. Redo reapplies the move+log in the same way as the original action.

Trigger is both global `Ctrl+Z` (via `EventControllerKey` even when Preview has focus) and an Undo button in the Action Bar between Prev/Next and the index counter (`sensitive = !undo_stack.is_empty()`, tooltip `Undo (Ctrl+Z)`), plus `Edit → Undo`; redo has a companion button. While a move+log is in flight, undo/redo are disabled (busy-ignore). The stacks are **in-memory only** for v1 — cleared on quit/crash, not durable. This keeps failure semantics simple: failure to move or log never advances, and undo itself can fail with a toast and stay.

Consequences: restart loses history, which is acceptable for short triage sessions; future durable undo would need a recovery log and is out of scope.
